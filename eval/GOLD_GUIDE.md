# 정답 사례 작성 지침 (Codex용)

이 문서는 **정답 데이터를 만드는 에이전트(Codex)** 와 그것을 검증하는 사람을 위한 지침이다.
규칙 엔진을 만드는 쪽(Claude Code)은 이 정답을 쓰지도, 고치지도 않는다. 두 쪽을 나눠야 "자기 채점"이 되지 않는다.

## 1. 독립성 규칙 (가장 중요)
- `config/policy.yaml`, `src/triage/priority/`를 **읽지 말고** 정답을 매긴다. 엔진의 가중치·임계값에 정답을 맞추면 측정이 무의미해진다.
- 판단 기준은 아래 2장의 **등급 정의**(업무 의미)와 공개된 사실(KEV 등재, EPSS, 벤더 권고, 수정 버전)뿐이다.
- 엔진 결과(`out/`, `eval/results/`)를 본 뒤에 정답을 바꾸지 않는다. 바꿔야 하면 사람이 결정하고 `gold_changes.md`에 이유를 남긴다.

## 2. 등급 정의 (업무 의미)
| 등급 | 의미 | 기대 조치 |
| --- | --- | --- |
| P1 긴급 | 지금 공격받을 수 있고 피해가 크다. 실제 악용이 확인되었거나(KEV), 외부에서 쉽게 악용 가능한 치명적 취약점이 중요한 서비스에 있다 | 즉시 조치(1주 안) |
| P2 높음 | 악용 가능성이 의미 있게 높거나 외부 노출 서비스의 고위험 취약점. 당장 터지지는 않아도 다음 배포에 반드시 넣어야 한다 | 다음 배포(1개월 안) |
| P3 보통 | 위험은 있으나 악용 가능성이 낮거나 내부망·저중요도 자산이라 피해가 제한적 | 정기 업데이트(분기) |
| P4 낮음 | 영향 없음이 확인되었거나(VEX, 해당 기능 미사용) 실질 위험이 거의 없다 | 모니터링 |

판단 순서(권장): ① 영향 없음이 명확한가 → P4 ② 실제 악용 확인(KEV)인가 → 대체로 P1 ③ 악용 가능성(EPSS)·심각도(CVSS)·외부 노출·자산 중요도를 종합.
이 순서는 정답자의 사고 순서일 뿐 숫자 기준이 아니다. 경계 사례는 근거에 왜 그 등급인지 쓴다.

## 3. 파일 형식: `eval/gold.csv` (UTF-8, 첫 줄 열 이름)
| 열 | 필수 | 값 | 설명 |
| --- | --- | --- | --- |
| case_id | ✔ | G01… | 중복 불가 |
| vuln_id | ✔ | CVE-2021-44228 | CVE 우선 |
| package | ✔ | `pkg:maven/org.apache.logging.log4j/log4j-core` 또는 `group:artifact` | purl 권장 |
| version | ✔ | 2.14.1 | 설치 버전 |
| ecosystem |  | maven, npm, pypi … | purl 이 아니면 적는다 |
| internet_exposed |  | Y / N / 빈칸(모름) | 자산이 외부에 노출되는가 |
| criticality |  | 1~5 / 빈칸 | 업무 중요도(5가 가장 높음) |
| kev |  | Y / N | **작성 시점** CISA KEV 등재 여부 |
| epss |  | 0~1 | **작성 시점** EPSS 값(소수, 예 0.9445) |
| cvss |  | 0~10 | CVSS v3.x 기본 점수 우선 |
| severity |  | critical/high/medium/low | CVSS 가 없을 때 |
| status |  | affected / not_affected | not_affected 는 VEX 등 근거가 있을 때만 |
| has_fix |  | Y / N | 수정 버전 존재 여부 |
| direct |  | Y / N / 빈칸 | 직접 의존성인가 |
| expected_tier | ✔ | P1~P4 | 2장 정의로 판단 |
| expected_order_group |  | 1, 2, 3 … | 전체 사례 중 급한 순서 묶음(1이 가장 급함, 같은 숫자는 동순위). 순위 상관 계산용 |
| rationale | ✔ | 한국어 1~3문장 | 왜 이 등급인지. 사실과 판단을 구분해서 |
| source_url |  | URL | KEV 항목, EPSS 조회, 벤더 권고 등 사실 출처 |
| reviewed |  | Y / 빈칸 | **사람이** 검증을 마쳤으면 Y. Codex는 비워 둔다 |

KEV·EPSS·CVSS 값은 사례 안에 고정한다. 나중에 외부 값이 바뀌어도 채점이 흔들리지 않게 하기 위해서다.
값은 작성일 기준으로 실제 조회해서 적고 `source_url`에 출처를 남긴다. 기억에 의존해 쓰지 않는다.

## 4. 사례 구성 (20건 권장)
분포가 한쪽으로 쏠리면 "다 낮게 매기는" 방식이 유리해진다. 등급마다 최소 3건 이상이 되도록 고른다.
- KEV 등재 건: 4~5건 (log4j 2.14.1의 CVE-2021-44228 포함, 내부망·저중요도 자산에 있는 KEV 건 1건 포함)
- KEV 아님 + EPSS 높음 + 외부 노출: 2~3건
- CVSS 높음(9 이상) + EPSS 매우 낮음: 2~3건 (심각도만 보는 방식과 차이를 보이는 사례)
- 내부망·저중요도 자산의 고위험 건: 2건
- 영향 없음(not_affected, VEX 근거): 2건
- 수정 버전 없음: 1~2건
- 결측(외부 노출 모름, EPSS 없음): 2건
- 중간 위험(CVSS 5~7, EPSS 낮음, 외부 노출): 2~3건

## 5. 작성 후 확인
```bash
uv run triage eval --gold eval/gold.csv --check   # 형식만 검증(채점 안 함)
```
형식 오류가 없으면 사람에게 넘긴다. 사람은 사례별로 사실(KEV·EPSS 값)과 등급 판단을 확인하고 `reviewed`에 Y를 적는다.

## 6. 예시
`eval/example_cases.csv`는 형식 설명과 채점 스크립트 동작 확인용 예시 3건이다. **정답이 아니며 측정에 쓰지 않는다.**
